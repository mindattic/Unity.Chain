# Unity.Chain: Project Bible

> The single source of truth for what Unity.Chain is, the rules that keep the rebuild faithful, how the code is
> organised, and every place it does not play exactly like the original, with the reason. `README.md` says how to
> build and run it; [`RECONSTRUCTION.md`](RECONSTRUCTION.md) is the full reverse engineering of the original and
> the build order to parity; [`chain-physics.md`](chain-physics.md) is the spring algorithm and its tuning.
>
> Anything here that is planned but not yet on main is marked **(planned, UNI-Tn)**. Nothing is claimed as built
> that is not.

## 1. The one sentence {#UNI-§1}

A mouse-steered angel flies an endless arena swinging a spiked mace on a spring chain, knocking down, grappling
and throwing a flock of enemies that home in on it, rebuilt from the 2005 VB.NET / DirectX 9 *Chain Game* (itself a
port of Philip Winston's 2000 *Elastic Trail* script) as a modern Unity 6 game.

## 2. The product promise {#UNI-§2}

- **The chain is the game.** Every link is a Hookean spring with drag and gravity, so the mace lags, swings and
  whips; circling the mouse winds it up like a flail, and the overhead boost keeps it from drooping when swung high.
- **Hit, grab, throw.** A mace hit knocks an enemy back by the mace's velocity over its mass and scores the damage
  x 1000. Hold the button and the mace grabs instead; release and the enemy flies off at the mace's velocity,
  bowling over any enemy it touches.
- **One arena, one loop.** 14 enemies seek the angel, 30 HP drains one touch at a time, one heart drifts down for
  +10, and at zero the light fades and the round resets itself.
- **Every knob of the original.** The `[` `]` chain length, the live spring, drag and gravity keys, gem link skins,
  backgrounds, lighting, screen shake, debug views and the script console all come across (most planned, see
  [RECONSTRUCTION §6](RECONSTRUCTION.md)).

## 3. What it is not {#UNI-§3}

- **Not a redesign.** No new modes, levels, enemies or progression. The scope is the original, played as it was
  meant to play (see [§4 rule 1](#UNI-LAW-1)), and the repo is finished when the last reconstruction story is.
- **Not a line-by-line port.** The code is rebuilt from scratch to current Unity practice; only the behaviour is
  kept.
- **Not frame-rate dependent.** The original's per-frame numbers are converted to a fixed step.

## 4. Design rules {#UNI-§4}

The owner's rebuild standard is in [`AGENTS.md`](../AGENTS.md); these are its rules as they apply here.

### {#UNI-LAW-1} Gameplay matches the original; broken things are fixed

Every value, unit and behaviour comes from the original source (`R:\...\Chain Game\`), never from a guess. Where the
original is plainly broken (a random that is not random, a draw call commented out, a feature that can never be
reached, sound that ships switched off) the rebuild plays the way the game was clearly meant to, and the fix is a
row in [§7 Fixed defects](#UNI-§7). Everything that works matches exactly. Anything else that differs is a row in
[§8 Deliberate deviations](#UNI-§8) with its reason. A difference with no row is a bug.

### {#UNI-LAW-2} Reverse-engineer before rebuilding

A module is read in full and recorded in `RECONSTRUCTION.md` before its rebuild starts.

### {#UNI-LAW-3} Core is pure C#

The rules live in an engine-free Core assembly (`noEngineReferences`, no `UnityEngine`) tested with `dotnet test`.
State changes only through commands, which produce events; presentation reads state and plays events and never
mutates the game.

### {#UNI-LAW-4} Hard assembly boundaries

Core, Runtime, Editor and Tests are separate asmdefs with one-way references (see [§5](#UNI-§5)).

### {#UNI-LAW-5} Content and tuning are data

Every tuning number lives in a data file or the settings registry and is validated on load (see [§6](#UNI-§6)).

### {#UNI-LAW-6} Built in code

The scene, UI and objects are composed in code (`SceneBuilder`, `PlayerBuilder`), never wired by hand in the
Inspector. Regenerate `Main.unity` rather than editing it.

### {#UNI-LAW-7} Modern Unity only

Unity 6, URP behind a pipeline-agnostic layer, the Input System through an action asset, UI Toolkit or the shared
MindAttic components, Unity.Shared profiles and settings, and multiplayer-ready seams: commands carry a player id,
one authority holds the state, no global current-player singleton, built on the Unity.Multiplayer kit.

### {#UNI-LAW-8} Done means seen working

Core tests green, a build that launches, and the feature seen in play (a screenshot or a scripted run) before a
ticket closes.

## 5. Architecture {#UNI-§5}

### 5.1 Target

```
 Unity 6000.4.3f1 · one scene, Assets/Scenes/Main.unity, generated by SceneBuilder
 ┌────────────────────────────────────────────────────────────────────────────────────┐
 │ Unity.Chain.Runtime  (MonoBehaviours, presentation, input, audio, HUD)              │
 │   reads Core state, plays Core events, turns input into Core commands               │
 └──────────────▲───────────────────────────────────────┬─────────────────────────────┘
                │ events / state                         │ commands (with player id)
 ┌──────────────┴───────────────────────────────────────▼─────────────────────────────┐
 │ Unity.Chain.Core  (noEngineReferences)                                              │
 │   ChainSimulation, AngelFlight, EnemyBrain, flocking, heart, GameState, clock,      │
 │   script language, settings registry, data loading and validation                   │
 └────────────────────────────────────────────────────────────────────────────────────┘
 Unity.Chain.Editor  → Runtime, Core   (SceneBuilder, PlayerBuilder, data tools)
 Tests/Core.Tests    → Core            (NUnit, dotnet test, outside Unity)
 Unity.Chain.EditMode/PlayMode.Tests → Runtime, Core (Unity Test Framework, adapters and the scene)
```

References only point down: Runtime → Core, Editor → Runtime/Core, tests → what they test. Core references nothing
Unity.

## 6. Data files {#UNI-§6}

**The original had none.** Its Jet `.mdb` databases are commented out and `loadTerrain` reads an unset `DataRow`;
every number is a field in code. The only persisted data is the registry (`HKCU\Software\MindAttic\Engine` read,
`...\War` written) with Width, Height, ColorDepth and Fullscreen.

**The rebuild today** keeps its tuning as `[SerializeField]` defaults on components and as `Config`/`Settings`
structs on the pure rule classes, each carrying the original's figure converted to world units per fixed step.

**The target (planned, UNI-T33):** one validated data file per concern, loaded by Core and rejected on load with a
message if any value is out of range:

| Data | Holds | Original source |
|---|---|---|
| chain tuning | link count, segment length, spring, drag, gravity, jitter stop, overhead boost, mace index range and scale, bounce | `Chain.vb` |
| angel | steer ratio, bounds, hover bob, flap rate, hand offsets, max HP, hurt delay | `Angel.vb`, `Engine.vb` |
| enemies | count, HP, mass range, seek rate, hurt deceleration, flocking push, frame rate | `Enemy.vb`, `Engine.vb` |
| heart | fall, sway, heal, cap | `Item.vb` |
| game | score multiplier, game-over fade step, clock, live-tuning key steps, game speed | `Engine.vb`, `Root.vb` |
| assets | sprite sets, link skins, backgrounds, sound sets, music | `Textures.vb`, `Sound.vb` |

Player options (resolution, window mode, volumes, mutes) replace the registry with a Unity.Shared profile
(planned, UNI-T36, UNI-T59).

## 7. Fixed defects {#UNI-§7}

Places where the original's code is plainly broken. The rebuild plays the way the game was clearly meant to.
Status: **fixed** (on main), **planned** (the ticket that fixes it).

| # | Defect in the original | Where | What the rebuild does | Status |
|---|---|---|---|---|
| D1 | Enemies spawn only at the four corners: `getRndNum(-1, 1)` returns the integers -1, 0, 1 and 0 is rejected, so every "random" spawn is (+/-1, +/-1) and all 14 start stacked | `Enemy.vb` `loadEnemy`, `Root.getRndNum` | spawns each enemy at a real random point in the arena (`EnemySpawner.RandomPositions`) | fixed (UNI-T21 settles the reset path) |
| D2 | The game is silent: `bSound` and `bMusic` default to `False` and `playSFX` is never called, though every clip is loaded | `Sound.vb` | sound and music on by default; swing, hit and death play their clip sets (`ChainAudio`), music loops (`MusicPlayer`) | fixed in code; clips planned, UNI-T20 |
| D3 | No HUD text is drawn: `Root.Write` has its `DrawText` commented out, so HP, score, grappled HP, readouts, clock and FPS never appear (earlier backups drew them) | `Root.vb` `Write` | draws the HUD (`GameHud`) | fixed (IMGUI); layout UNI-T50, UI Toolkit UNI-T37 |
| D4 | The magnet mace can never be reached: `theMaceMode.Magnet` is declared and `magnet.PNG` loaded, but nothing ever selects it | `Chain.vb` | a selectable magnet mace skin | planned, UNI-T43 |
| D5 | A thrown enemy never slows: no drag and no end state, so it leaves the arena for good | `Engine.vb` `checkThrowImpact`, `Enemy.vb` | a thrown enemy goes Hurt and decelerates like a knocked one, then seeks again (`EnemyBrain.Throw`) | fixed (UNI-T45 checks the rate) |
| D6 | The day cycle never advances: `dayLength` is 1e10 s, so Day, Dusk, Night and Morning never change in play | `Lights.vb` | the cycle runs at a playable length | planned, UNI-T46 |
| D7 | The chain is pulled from one side: the port turned the JS original's two `If`s into `If / ElseIf`, so only the previous link's spring ever fires | `Chain.vb` `renderChain` | each link is pulled by both neighbours, as in *Elastic Trail* (`ChainSimulation`) | fixed (UNI-T45 settles the feel) |
| D8 | The mace drifts: `link(Mace).X/Y += maceOffset` is added every frame, cumulatively, instead of once as a sprite offset; a stray `link(1).Y -= 0.0004` "fix" does the same | `Chain.vb` `renderChain` | the offset is render-only; no fudge term | fixed |
| D9 | Speed depends on the machine: every number is per frame with no time step and no frame cap | `Form1` loop, all modules | a fixed step; per-frame figures converted at 60 fps | fixed (UNI-T45 matches the felt speed) |
| D10 | Off-by-one HP: the HUD draws `HP + 1` bars and the game ends below zero, so 30 HP takes 31 hits | `Engine.vb` `renderDisplay`, `GameOver` | exactly HP bars; game over at 0 (`GameState`) | fixed |
| D11 | Some swings do no damage: damage is `abs(dX + dY/2)`, which cancels to zero on certain diagonals | `Engine.vb` `checkMaceImpact` | damage from mace speed (`MaceHitDetector`) | fixed (UNI-T45 matches the scale) |
| D12 | Fast swings pass through enemies: one AABB at the mace link per frame | `Engine.vb` `checkMaceImpact` | swept circle from the last position to this one | fixed |
| D13 | Game speed does nothing: Minus/Equals change `gameSpeed` and the HUD shows it, but it is never applied | `Engine.vb`, `Form1.OnKeyDown` | game speed scales the step | planned, UNI-T52 |
| D14 | The joystick binds nothing: axes and buttons are read and ignored | `Input.vb` | a gamepad drives the same actions as the mouse | planned, UNI-T34 |
| D15 | The background toggle key is unreachable: a second `Case Keys.B` sits below the first | `Form1.OnKeyDown` | B and N both reach their backgrounds | planned, UNI-T40 |

Not restored, on purpose: stubs with no body (`ExtraLife`, `Health5`, `Health20`, `Money` items; `Center` and
`Wander` motions; the `Wander`, `Retreat`, `Limbo`, `Death` AI states; `angelAI.Hurt`; `bRicochet`; the terrain
lines; the cursors; `renderTime`, `renderDate`, `levelText`; `SetupLights`). Restoring them would mean inventing the
behaviour, not fixing it. `Cautious` and `Align` have code but no rule for when they apply; they stay out unless the
owner decides otherwise.

## 8. Deliberate deviations {#UNI-§8}

Working behaviour of the original the rebuild does differently, and why. Status: **kept** (the deviation stays),
**to settle** (a ticket brings it back in line or decides), **temporary** (an intermediate step until the ticket).

| # | Original | Rebuild | Why | Status |
|---|---|---|---|---|
| V1 | 45 degree perspective camera at z -1, fixed 4:3 | orthographic `CameraRig` that fits the whole level on any aspect, or follows through a dead zone | 2D in Unity, any screen shape without stretching or showing past the arena | kept; perspective data and the debug camera, UNI-T57 |
| V2 | Units are the camera's NDC-like plane (half-height 0.414) | world units; every figure converted, mostly as fractions of the play area | Unity physics, sprites and cameras work in world units | kept |
| V3 | All 25 links simulate; only 0..`Mace` are drawn | only 0..`Mace` simulate; the rest park on the mace and pay out from it when lengthened | with both-neighbour pull (D7) an undrawn tail would drag the mace | kept, follows D7 |
| V4 | Chain wall bounce commented out | links bounce off `LevelBounds` at 0.5 (`keepInLevel` turns it off) | *Elastic Trail* bounced; keeps the mace on screen | to settle, UNI-T45 |
| V5 | Angel contact rectangle X..X+0.06 by Y+0.03..Y+0.15 | a Physics2D circle | fits the sprite at any scale and with Physics2D queries | kept |
| V6 | Flocking pushes 0.0005 per axis per frame | 1.5 world units per second | first version guessed the value | to settle, UNI-T35 |
| V7 | The heart is gone after a pickup until `Reset` | it returns to the top and keeps drifting | first version guessed the behaviour | to settle, UNI-T44 |
| V8 | Pause is the Pause key; Escape quits | P or Escape pause | interim keys before the input pass | to settle, UNI-T54 |
| V9 | `- PAUSE -` and HUD as plain D3D text | IMGUI `GameHud` | interim | temporary, UNI-T37, UNI-T50 |
| V10 | Swing whoosh, hit, death; no catch or throw sounds | adds catch and throw sounds; the swing fires on mace speed relative to the hand | flying with a trailing mace is not a swing; catch and throw needed feedback | to settle with the clips, UNI-T20 |
| V11 | `music.wma` | the same track converted | Unity cannot import WMA | kept |
| V12 | 640x480 borderless form, options in the registry | resizable window (1600x900 today), options in a Unity.Shared profile | modern displays; the shared settings standard | to settle, UNI-T38, UNI-T36, UNI-T59 |
| V13 | Input by exclusive DirectInput mouse delta and key polling | Input System (polling today) | the modern Unity input stack | kept; action asset UNI-T34 |
| V14 | F1-F3 switch D3D wireframe, textures and culling | the nearest URP equivalents | the D3D render states do not exist in URP | planned, UNI-T56 |
| V15 | Game over then `Reset` in place | the same fade, then a scene reload or an in-place reset | both end in the original's state | kept |

### Keeping these tables current

Every ticket that changes how the rebuild plays relative to the original updates §7 or §8 in the same commit: add a
row for a new difference, change a row's status when it is settled, and delete nothing (a settled row says
**matches**). A difference found with no row is a bug: file a ticket.

## 10. Glossary {#UNI-§10}

- **Link**: one point of the chain; link 0 is pinned to the angel's hand.
- **Mace**: the heavy end link at index `Mace` (1..12, default 6), drawn 3.5x.
- **Grapple**: holding the button turns a mace hit into a grab; release throws.
- **Hurt**: an enemy's knocked-back state; it decelerates, then seeks again.
- **Thrown**: a Hurt enemy launched by the grapple; it knocks over the enemies it touches.
- **Reset**: the original's full round restart (score, timer, light, angel, enemies, heart, music).
- **The original**: the VB.NET / DirectX 9 Chain Game at `R:\...\Chain Game\`.
